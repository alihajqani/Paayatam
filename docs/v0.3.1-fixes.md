# v0.3.1 — eight reports from production

**Branch: `feature/v0.3.1-product-fixes`, on top of `v0.3.0` (`a138d9a`).**

Eight items came back from using v0.3.0: five bugs, three feature requests. This
records what each one actually was — several were not what the report said — and
the shape of the fix.

## 1. The policy gate was a dead end

**Reported:** "After a policy update the system says *read and accept the
policies*, but there is no UI to view the policy text or an accept button."

**What it actually was.** The UI existed. `TermsView` renders every current
document, shows which are outstanding, carries the checkbox and the accept
button, and the router sends anybody with a pending policy to it. All of that
shipped in v0.3.0 and all of it worked.

What did not exist was any way for the client to *find out*. `pendingPolicies` is
loaded once, at sign-in. An admin publishing a version mid-session therefore left
the client believing nothing was outstanding while the server refused every gated
write with `POLICY_VERSION_STALE` — and `/terms` is only routed to when the
router already knows a policy is pending, which is exactly the thing the client
had no way to learn. So the user read the sentence and could not reach the screen
that answers it. Every subsequent tap said it again.

**The fix.** A gate hook in the Mini App's HTTP client: `POLICY_VERSION_STALE` or
`TERMS_NOT_ACCEPTED` re-reads `/me/policies` and, if something really is
outstanding, routes to `/terms`. In the client rather than in each view, because
the refusal comes back from any gated write and a per-screen recovery is one that
is missing from the screen nobody thought about. The error is still thrown: the
request did fail, and swallowing it would leave a screen rendering a success it
never got.

Two smaller holes in the same report:

- `/terms` has been re-openable since v0.3.0 and **nothing linked to it**, so the
  only route to the document was being blocked by the gate. Home now carries a
  permanent link, badged when something is pending.
- A deployment with no published policy rendered a skeleton *forever*, because
  "not loaded yet" and "there is nothing" looked identical. It now says so —
  which is the correct state, since `hasAcceptedCurrentPolicies` returns true for
  an empty required set and nothing is gated.

## 2 and 3. One mandatory channel became several, and the gate now stops people

Two reports, one piece of work.

**Reported:** "Only one channel can be made mandatory; we need multiple, with the
order of joining and display mattering." And: "Mandatory membership is not
enforced in the mini-app."

### The data

v0.3.0 put the channel's public face on the settings singleton — one
`chat_identifier`, one `public_username`, one `invite_url`. That shape holds
exactly one channel.

Migration `0024` adds `required_channel`: a row per channel, with a title the
*user* reads, a sparse `sort_order`, and an `is_active` flag. The singleton keeps
what is genuinely global — whether the requirement is on, which actions it
covers, whether Telegram is asked. **Its three per-channel columns are left in
place and are no longer read**: dropping them would be a destructive statement in
a feature release, and keeping them costs three nullable columns on a one-row
table.

The backfill copies whatever channel the deployment already had into position 1,
guarded on there being something to copy and on the table being empty. Rehearsed
against four states before shipping: a configured channel (copied with its
identifier, link, order and active flag), a private invite with no username (the
title falls back to «کانال پایه‌تم»), nothing configured (**no row**, so no
requirement appears out of nowhere), and the statement run three times (one row).

### The rule

A user passes when **no** active channel refuses. That is not "passes the first
one", and deliberately not "every channel said `MEMBER`" either — the second
reading would turn one misconfigured channel in a list of four into an outage for
everybody. The outcomes are combined by *does any channel authoritatively
refuse*, so the fail-open property v0.3.0 established survives the list.

`telegram_account` is read once per check rather than once per channel.

### The enforcement

The gate existed but only as a banner above two forms, so *"mandatory membership
does not work in the mini-app"* was fair: a banner on a screen full of other
things to tap is not a block.

`APP_ACCESS` is a fifth gated action and the router treats it as one — every
navigation goes to `/join-channels`, a screen that lists the channels in the
operator's order with a join button each and a re-check that clears Telegram's
cached answer for all of them.

**It is deliberately not in `AuthGuard`.** A gate over every authenticated route
would also refuse `/me`, `/me/policies` and the membership check itself, which
are the three calls the screen that clears the gate is built from — so switching
it on would lock the product shut with no way back. The consequence is stated
rather than hidden: somebody who bypasses the Mini App can still read what the
API exposes, and is still refused every one of the four real operations the
moment they attempt one.

### The panel

`/channel` gains the list: add, activate, deactivate, remove, and «↑»/«↓» which
send the **whole order back** rather than a move instruction — the one
formulation that cannot produce an order neither side intended.

Two states the API refuses outright, both being the same mistake seen from
different ends: requiring membership with no reachable channel, and removing the
last active channel while the requirement is on.

## 4. The interest picker did not know its own limit

**Reported:** "User can select more than 10 interests. They get an error but the
UI does not disable further selections."

Exactly right. The server always refused more than ten; the picker had never
heard of the number. A user could tick fifteen chips — watching the counter read
«۱۵ از ۱۰» while they did it — complete the rest of the form, submit, and learn
about the limit from a 400.

`MAX_PROFILE_INTERESTS` now lives in the shared contracts, read by both zod
schemas and by the Mini App: a cap the client cannot read is a cap the client
will get wrong. The rule is a composable both profile screens share, so it is
testable without a component harness this repository does not have.

At the cap, every **unselected** chip is disabled and a sentence says why.
Selected chips stay live — the way out of a full list is to untick something, and
disabling those too would be a dead end with no message. A refused tap still gets
a haptic, and a different one: silence is indistinguishable from a tap that
missed.

## 5. Publishing is two options, and invitations stay in the city

**Reported:** "The publish section shows VIP channels and other channels, but I
have one channel for events."

The section offered four things: a boost, permanent VIP, a channel post and a
top-20 invitation — the first two sold as placements in a «کانال ویژه» that does
not exist on a deployment with one channel. A host was asked to choose, and pay,
between two options that were the same option in a place that was not there.

`PromotionDialog` is deleted and nothing links to it. What remains is the
decision a host actually makes: **15 coins** to publish to the channel, or **10**
to reach the twenty most likely to come.

The boost and VIP *endpoints* are untouched and no data was migrated. An event
that already carries either keeps it and still ranks on it; it is simply no
longer described to a host as something to buy. Removing the columns would have
been a destructive change in a release that did not need one.

**Invitations now go only to people in the event's city.** The pool was "in this
city **or** interested in this category", which gave the score's city term some
ordering power and gave the product spam: an invitation says *be at this place on
this evening*, and sending it four hundred kilometres away is not a ranking
mistake, it is the wrong message. The city is a filter now. `sameCity` in
`score.ts` consequently fires for everybody and contributes nothing to the
order — kept, because the preview reports its reasons in aggregate and a
breakdown that stopped counting the city would read as though nobody was in it.

A host in an empty city gets zero recipients, is told so by the preview, and is
charged nothing — the outcome the preview already promised.

> **On "special or advertising channels, manageable from the admin panel".** The
> `required_channel` table and its screen are that place for *membership*
> channels. The bot's **posting** destination stays `TELEGRAM_CHANNEL_ID`, an
> environment variable, and that is a security decision rather than an oversight:
> a destination editable from a web session is a destination an attacker with a
> session can redirect. Adding a second posting target is a schema change plus a
> publishing selector; it is not in this release, and nothing here blocks it.

## 6. The guest-to-host flow

**Reported:** "The process of messaging in the bot, going to the app, confirming,
giving phone number, etc. is too complicated. Redesign it like a product
manager."

Three cuts, each removing a **context switch** rather than a click.

### Say hello with the request

The old flow: tap join, read *"your conversation is open in Telegram"*, close the
app, find the bot, work out which of several conversations this one is, type.
Four actions between deciding to come and being able to say anything — and the
host meanwhile holds a request from a stranger with no words attached, which is
the decision they are worst equipped to make.

The event page now carries one optional line, sent with the request.

It is a **second request**, not a field on the join. `POST /events/:id/join`
takes no body by design — *"there is no field here for a client to be wrong or
dishonest about"* — and a note on it would need the sanitizer, the contact
masking and the cipher reachable from inside the join transaction. The note goes
through the relay that already does all three.

A failed note does not fail the join. The seat is scarce and the greeting is not;
rolling back over a network blip would hand the place to somebody else, and the
guest can retype a sentence.

### One tap into the conversation

`webApp.close()` returns the user to *whatever chat they opened the app from* —
the bot for somebody who launched it there, the **channel** for somebody who
tapped a post's button. The second case is exactly the person then told to go and
find the bot. `openTelegramLink` lands them in the bot chat whichever door they
came in by; the catalog carries the bot's username, which is public and already
in every deep link the product emits.

### Contact sharing without leaving Telegram

This is the "giving phone number" step, and it is worth being precise about what
it is: **the platform holds no phone number and will not surrender a Telegram
handle.** Agreeing does not disclose anything. What changes is that the sharer's
*own* messages stop being masked, so they can send their details themselves if
they choose to.

The old route was: read the message in the bot, open the Mini App, find the
conversation in a list, tap through a confirmation. Now `chat:share` asks and
`chat:shareyes` does, with a message in between saying exactly what agreeing
changes. **The confirmation stays** — consent to disclose is the one decision in
this product that has to be unambiguous (ADR-0009), and a single tap on a button
attached to a message that arrived unbidden is not it. What goes is the trip to
another application to give it.

The button is rendered only on an accepted conversation, from a payload flag that
defaults to false, because a message queued by an older deploy that carries no
flag must not put an irreversible disclosure one tap from an anonymous chat.

## 7. The channel post has a button

**Reported:** "Events are posted to the channel but there is no link to the event
page. Use a Telegram inline button."

There was a link — an `<a>` in the last line of a nine-line message. It works,
and almost nobody taps it: it renders as ordinary blue text at the bottom of a
wall of detail and competes with everything above it.

It is now an inline button: full width, under the post, where every Telegram user
already expects a control. Same deep link, same public id, so nothing about what
is exposed changed. `postToChannel` takes the keyboard, and text and keyboard
come out of **one** renderer — two call sites is how a post ends up with a button
pointing at a different event than its body.

A URL button, never a callback: a channel post has no session behind a tap, and
`callback_data` from a public channel would reach the bot with nobody attached to
it.

## 8. The disclaimer

**Reported:** "Above every event, display that Payetam has no responsibility and
the user must be careful. In the mini-app and the bot."

One string in `@payetam/shared`, in a full and a one-line form, because a
liability sentence that appears in four surfaces and is edited in three is a
sentence the product is now telling different stories about.

| Where | Form |
|---|---|
| The event page | Full — the screen somebody is actually deciding on |
| The head of the discovery list | Compact, **once** |
| Every channel post | Compact, above the event's own details |
| The paid invitation | Compact — an advertisement in a stranger's inbox |
| The acceptance notification | Compact — a meeting with a stranger becoming real |

**Once at the head of a list, not on every card.** Repeating it twelve times on a
scrolling screen is the literal reading and the worse one: a sentence people see
that often is a sentence they learn to look past, which is the one failure a
disclaimer cannot afford.

## What the release-leak scan found

Not a report, but the most serious thing this release fixed.

`response-leak.int.test.ts` scans every endpoint for four identity patterns.
Adding four admin endpoints to it surfaced that **no admin write's success
response had ever been scanned**: `adminCookie` held the first throwaway session
while `adminCsrf` was overwritten to the *last* one's token, so `AdminGuard`
compared a token belonging to session Z against a cookie belonging to session A
and refused every `POST`, `PUT`, `PATCH` and `DELETE` on the admin API with
`FORBIDDEN {reason: 'csrf'}`. The scan then dutifully searched those refusals for
leaks and found none — a security test passing for the wrong reason, across four
milestones.

Pairing the cookie with its own token fixes it. The scan now reaches the admin
write paths, and a channel's own handle is **redacted rather than exempted**, so
a *person's* handle still fails on the same routes with the same patterns.
