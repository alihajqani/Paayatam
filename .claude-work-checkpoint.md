### Two production-stopping bugs, found by running things that had not been run

**F1 — neither process would have started.** M22 wired
`ChannelMembershipService` into `EventService`, `ParticipationService` and
`InvitationService` **without adding `ChannelModule` to the three modules that
declare them.** Nest scopes providers to the declaring module, so importing both
into the root is not enough. The API *and* the worker would have failed at boot —
containers that never become healthy. Found by the response-leak scan, which is
the only test that builds a real graph and had not been run since those phases
landed. Fixed; `app.module.test.ts` in both apps now resolves each graph with
Nest's `preview: true` (no DB, no Redis, no queue consumers) and was verified to
fail when the fix is removed.

**F2 — every gated write refused, for every user, on a deployment with no
published legal text.** `ConsentService.hasAcceptedCurrentPolicies()` returned
`false` when no required policy version exists, and `AuthGuard` turns that into
`POLICY_VERSION_STALE`. So a fresh install — or any deployment whose terms are
still in draft — refused event creation, joins, invitations and chat writes, and
told the user to go and re-read a document that did not exist. It also
contradicted `standingFor()`, which correctly reported nothing pending, so the
client believed it was clear while the server refused. One line: `return true`
on the empty set. That is not a hole — "never accepted anything" is a different
question, already answered earlier in the guard by `onboardingState === 'NEW'`.
Two regression tests in `policy-gate.int.test.ts` pin both directions.

**This one directly governs the deploy.** If production has no published
TERMS/PRIVACY version, shipping M22 without this fix would have bricked the
product. Checking production's `policy_version` table is a required
pre-deployment read.

### Also fixed

`catalog.service.int.test.ts` asserted the promotion-price list exactly and had
not been updated when phase 5 added four fields. The values were right
(5 / 15 / 10, cap 20); the assertion was stale. Kept `toEqual` rather than
loosening to `toMatchObject` — an exact list is the point.

### The critical fix, in one paragraph

M22 wired `ChannelMembershipService` into `EventService`, `ParticipationService`
and `InvitationService` **without adding `ChannelModule` to the three modules
that declare them.** Nest scopes providers to the declaring module, so importing
both into the root is not enough. **Both the API and the worker would have failed
to start on deploy** — a container that never becomes healthy, not a failing
request. Nothing caught it: unit tests use `new`, integration tests assemble by
hand, and the only test that boots a real graph is the response-leak scan, which
had not been run since these phases landed. Two new `app.module.test.ts` files
now boot both graphs with Nest's `preview: true` (resolves everything,
instantiates nothing, needs no database) — verified to fail when the fix is
removed.

### Deliberate architectural exceptions (documented in code)

- `apps/api/src/telegram/membership.probe.ts` calls `getChatMember` **from the
  API**, which is a bounded exception to invariant 11 (all outbound Telegram in
  the worker). Justification: it is a synchronous read a user is waiting on; one
  method only; Redis-cached 120 s; rate-limited; fails open.
- The membership gate **fails open on every outcome except an authoritative
  `NOT_MEMBER`**, so a Telegram outage degrades the gate rather than the product.
- The 30-second policy cache in `ConsentService.currentPolicies()` was
  **removed**. It caused stale `POLICY_VERSION_STALE` refusals — on the release
  where everybody is asked to re-accept at once it would refuse the very
  acceptance that clears the gate. The comment in the file records why.
- `ledger.drift` reports and never repairs. Auto-correcting would either
  overwrite a balance a user is holding or write a plug entry into an append-only
  ledger; that is a judgement call with money attached.
